# Product Requirements Document (PRD)

# Digital Companion for Field Drug Testing

## 1. Product Overview

### Project

Digital Companion for Field Drug Testing

### Problem Statement

Smart India Hackathon 2026 — PS-231

### Purpose

The Digital Companion for Field Drug Testing is a software system designed to assist officers during presumptive field drug testing using existing colour-change testing kits.

The system does not replace the physical testing kit or laboratory confirmation.

Instead, it provides a digital workflow around the existing testing process:

1. Select the substance/test being performed.
2. Load the corresponding reference colour information.
3. Capture or upload an image of the completed field test.
4. Verify image quality.
5. Detect the reference colour card.
6. Detect the reaction/test area.
7. Calibrate colour measurements using the reference card.
8. Compare the reaction against the expected reference.
9. Produce a Positive, Negative, or Inconclusive result.
10. Store the complete test record.
11. Generate a tamper-evident record using hashing.
12. Allow later verification and review.

The result is intended as a presumptive field-testing result and not as laboratory confirmation.

---

# 2. Goals

## Primary Goals

- Digitize the field drug-testing workflow.
- Reduce dependence on manual visual interpretation.
- Standardize colour analysis.
- Account for lighting differences using a reference colour card.
- Associate every analysis with the correct drug/test definition.
- Produce deterministic and explainable classification.
- Maintain a searchable digital history of tests.
- Preserve evidence associated with each test.
- Detect later modification of stored test records.
- Provide a verification mechanism for stored records.

## Secondary Goals

- Provide a simple workflow for field officers.
- Reduce manual record-keeping.
- Provide supervisors with access to historical test results.
- Make the system modular enough for additional tests and substances to be added later.

---

# 3. Non-Goals

The system will NOT:

- Replace laboratory confirmation.
- Perform chemical identification directly.
- Claim that image analysis alone can identify an unknown substance.
- Automatically determine an unknown drug without a selected test definition.
- Replace the physical field-testing kit.
- Provide forensic-grade conclusions from a photograph alone.
- Depend on cloud AI services for the core classification logic.
- Require new physical hardware for the prototype.

Responsibilities:

- Inspect stored evidence.
- Verify record integrity.

6. Test Definition / Drug Database

The classification system must know which test is being performed.

A photograph by itself is insufficient because the expected colour reaction depends on the selected test.

Therefore, the application maintains a structured test-definition database.

For the current prototype, the database is stored as JSON.

Each test definition contains information such as:

Test ID
Drug/substance name
Alternative/common names
Test name
Test category
Reference colour
Reference shade
Reference colour HEX value
Expected reaction information
Detection notes
Classification configuration
Status

Example:

{
  "test_id": "TEST-001",
  "substance": "Example Substance",
  "test_name": "Example Colour Test",
  "category": "Field Presumptive Test",
  "reference_colour": {
    "group": "Yellow",
    "shade": "Shade 1",
    "hex": "#F0DC78"
  },
  "classification": {
    "positive_distance": 45,
    "negative_distance": 25,
    "positive_hue_tolerance": 12,
    "negative_hue_tolerance": 8
  }
}

The database is designed so additional test definitions can be added without modifying the classification engine.

11. Reaction Area Detection

The system identifies the reaction/test area separately from the reference card.

Measured colour

The reaction area must be successfully detected before classification.

12. Colour Calibration

The reference card is used to compensate for differences between:

Expected reference colour
Colour actually observed in the image

The system calculates RGB correction factors.

Conceptually:

Expected Reference RGB
        ↓
Measured Reference RGB
        ↓
RGB Correction Factors
        ↓
Reaction RGB
        ↓
Calibrated Reaction RGB

This allows the system to reduce the effect of lighting/camera differences.

15. Classification Safety

The system should return Inconclusive when:

Reaction information is unavailable.
Reference information is unavailable.
Reaction detection confidence is too low.
Reaction colour is insufficiently uniform.
Colour measurements fall between positive and negative boundaries.

The system must not force a binary answer when the available evidence is insufficient.

19. Tamper-Evident Records

After a test record is finalized, the system will calculate a cryptographic hash.

The hash will be based on the relevant stored record/evidence.

   ↓

   ↓

   ↓
Stored Integrity Value

If the stored information changes later, recalculating the hash should produce a different value.

19. Error Design

Errors should identify:

What failed.
Why it failed when known.
What the user should do next.

Bad:

Analysis failed.

Better:

Reference card could not be detected.

Make sure the reference colour card is
visible and capture the image again.

[ Retake ]
20. Inconclusive Result Design

An inconclusive result must not look like a system failure.

It is a legitimate analysis result.

Example:

INCONCLUSIVE

The available colour evidence does not
clearly fall within the positive or
negative range.

Review the image or perform the physical
test again according to the applicable
testing procedure.
21. Loading States

Long-running operations should show progress.

Example:

Analyzing...

Image quality        ✓

Colour calibration   ●

This makes it clear that the application is still working.

22. Empty States

Test history:

No test records found.

Completed tests will appear here.

Search:

No matching tests found.

Try another substance, test name,
or record ID.
23. Responsive Design

The application should work on:

Desktop
Laptop
Tablet

The capture interface should prioritize the camera/image area.

The sidebar should collapse when screen width requires it.

24. Visual Design Principles

The UI should use:

Clean cards
Clear spacing
Strong typography hierarchy
Consistent borders
Consistent button styles
Minimal unnecessary decoration
Clear status indicators

The interface should feel like an operational application rather than a generic dashboard template.

25. Accessibility

Important information must not rely only on colour.

For example:

✓ Positive
✓ Negative
! Inconclusive
✕ Error

Text labels should accompany status indicators.

Buttons should have clear action labels:

Capture Image
Retake Image
Upload Image
Analyze Test
Save Test
Verify Record
26. Design of AI-Assisted Classification

The system should not present the classifier as an all-knowing AI.

The UI should communicate that the system analyzes the selected test definition and image evidence.

Example:

Analysis Basis

Selected Test:
Example Colour Test

Reference:
Yellow — Shade 1

The result was generated from:
• Reference-card measurement
• Reaction colour
• Colour calibration
• Hue difference
• Reaction uniformity

This makes the system more transparent.
